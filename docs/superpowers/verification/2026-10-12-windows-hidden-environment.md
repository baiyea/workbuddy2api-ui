# Windows 安装后自动启动失败修复

## 根因与修复范围

- 用户使用的 `wb2api-desktop-windows-x64-0.2.0 (1).exe` SHA-256 为 `cedb4ced51a8b1fcb08b63c78e7876c0fc4c3e899980a0fd75ffcb5f28f31bd6`，与此前发布的减包安装器一致。
- 用户反馈仅安装完成后的自动启动出现 `invalid environment variable name`。只读检查该失败进程的环境块，确认存在隐藏变量名 `=::`；没有输出或保存环境变量值。
- `desktop/src/windows_process.rs` 原先仅允许 `=C:` 形式的隐藏变量名，导致 `=::` 被拒绝，core/console 尚未启动。
- 修复允许环境变量名开头的 `=`，继续拒绝空名称、后续分隔符及嵌入 NUL，保留 Unicode 比较、大小写覆盖和原子 Job Object 绑定。
- 未修改 WebView2 配置、Python、Go 服务、Docker 或用户数据路径。

## 回归验证

- 先增加 `=::`、`=ExitCode` 回归测试，在旧实现上得到与用户相同的错误；其余环境变量测试通过。
- 修复后 Windows 原生 `cargo test --all-targets`：13 项通过，1 项资源集成测试默认忽略。
- 显式执行资源集成测试通过：隔离空账号目录，启动 core/console、登录与任务目录、重启后密钥保留、退出清理。
- 再向集成测试进程显式传入 `=::`、`=ExitCode`，相同原生资源集成测试通过。
- `rustfmt --check`（修改文件）通过；初次检查发现的新增测试格式已修正。

## 本机安装验收

- `npm --prefix desktop run build` 生成 Windows x64 的 v0.2.0 修复包：36,391,813 字节（34.71 MiB）。构建期临时同步版本号，完成后恢复原有清单与锁文件。
- 安装包 SHA-256：`bbe37d03e9b6a360520c3ac6ad474a8356e9b2dd0aab62704737f6be0d83b909`；7-Zip 完整性检查通过。
- 安装前将现有 8 个数据文件完整备份至本机应用数据目录之外。用户从托盘退出失败实例后，执行 `/S /UPDATE /R` 覆盖安装，由安装器自动启动应用。
- 实际安装路径下的主程序、core、console 均运行，监听 `127.0.0.1:7863`；`/` 与 `/livez` 返回 200。
- 安装并启动后无数据文件丢失，6 个文件哈希不变，仅两份 core 日志发生正常写入/轮转。
- 安装后的主程序与安装包内解出的主程序 SHA-256 一致：`5addd8feb581a2ae02f17d1f77f293c18d0af393015cc085a69b8ddb4424ae57`。
- 修复安装包另存至用户下载目录，名称为 `wb2api-desktop-windows-x64-0.2.0-env-fix.exe`，保留原下载包。

## 验证边界

- 静默安装 `/R` 与安装完成页调用同一 `RunAsUser` 启动函数；本次静默自动启动的实际环境没有 `=::`。对该变量的精确复现与修复验证来自失败进程取证、回归测试和显式传入隐藏变量的原生集成测试，不声称重新点击了 GUI 安装完成页。
- 没有验证真实上游账号任务或干净 Windows 机器。以上为发布前的本地验收记录，未运行 CI；不涉及 Docker 发布。
