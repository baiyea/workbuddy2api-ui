# 纯净上游、构建补丁与自动任务控制台

## 1. 已确认目标

维护一个属于用户的独立定制仓库，集中保存 Docker 部署、Web UI 和适配代码。上游源码作为固定版本的纯净快照保存在 `upstream/`；不再把日常定制直接写入上游文件，也不通过持续合并上游历史维护分叉。

服务器取得本仓库源码并安装 Docker Compose 后，执行 `docker compose up -d` 即可启动，通过一个网页入口完成账号授权、状态查看、对话测试和自动任务管理。首次取得管理密钥以及上游扫码、验证码、地区选择仍由用户完成。

用户已逐项确认：

- 上游可以少量打补丁，但工作目录中的纯净上游不受构建影响。
- 当前目录作为定制仓库，内部增加 `upstream/`；接受多个容器、一个对外入口。
- 上游更新由用户主动触发，验证通过再部署；正常启动不追踪最新版本。
- 自动任务第一版只查看配置、查看记录和立即执行，不在网页编辑开关或时间。
- 手动执行面向全部符合条件的账号，不提供单账号选择。
- 最近执行记录跨重启保留；无法确认的积分收益不得显示为已到账。

本设计取代 `2026-09-15-docker-web-console-design.md` 中的单容器、直接修改上游和不包含任务页面的限制。原设计的鉴权、人工授权、安全保存凭据、流式取消和 CLI/API 兼容要求继续有效。

## 2. 基线与方案选择

初始上游基线为 `https://github.com/Sliverkiss/workbuddy2api` 的 commit `c576b489fa22e3c156e960ee6336c4e653a0d95c`。此次先迁移现有功能，不同时升级上游；网络代理地址不作为上游身份。

已检查基线：原 HTTP 服务提供 `/v1/chat/completions`、`/v1/models`、`/status` 和 `/healthz`；启动时加载账号并启动一个 scheduler。没有供网页直接调用的账号热安装、任务触发和持久执行记录接口。签到已有结构化结果，其他任务部分仅记录日志或子进程退出结果。

三种方案中选择第二种：

1. 完全零补丁、外部脚本包裹：上游最纯粹，但难以实现安全的运行时账号更新，以及自动与手动任务统一记录和互斥。
2. **纯净上游快照 + 独立扩展 + 少量构建补丁**：业务继续复用上游；补丁只承担接线、必要观察点和兼容性修复。
3. 继续直接改上游文件：当前功能迁移成本低，但后续合并与维护成本不符合用户目标。

不承诺补丁只改固定的两三个文件。验收看职责是否必要、改动是否隔离、是否有回归测试，不以隐藏改动或取消安全校验来减少文件数量。

## 3. 仓库与构建边界

```text
workbuddy2api/
├── upstream/              指定 commit 的纯净源码快照
├── upstream.lock          来源 URL、完整 commit、源码清单校验
├── console/               独立 Go Web 服务与原生 HTML/CSS/JS
├── extensions/            注入 core 构建目录的新增 Go 文件及适配测试
├── patches/               有序补丁、用途和受影响文件说明
├── deploy/                镜像构建、初始化和迁移配置
├── scripts/               构建准备、检查、上游更新及验收入口
├── docs/superpowers/      设计、实施计划与验收记录
└── docker-compose.yml
```

`upstream/` 作为普通源码快照纳入定制仓库，不使用需要额外初始化的 Git submodule，不包含嵌套 `.git`、真实配置、账号或运行数据。保留上游许可证和必要声明。锁文件对应可重复计算的源码清单，包含内容及有意义的文件模式信息。

构建顺序：验证锁文件及纯净快照 → 复制到临时构建目录 → 复制新增扩展文件 → 按顺序检查并应用补丁 → 编译与测试。扩展文件不得静默覆盖上游同名文件；必须修改既有文件的内容要明确写成补丁。源码不匹配、扩展重名、补丁冲突、重复应用或测试失败均停止，不使用忽略失败的兜底。

`console/` 独立编译。`extensions/` 的 core 代码放入临时上游 Go module 的适当包路径编译，合法复用现有 `internal` 包；不复制一份上游账号池、任务实现或调度算法来规避 Go 包边界。工作目录中的 `upstream/` 在整个过程前后校验一致。

默认 Compose 只使用本仓库已锁定的源码构建。首次构建仍需要获取基础镜像和依赖，不宣称离线可用；已有镜像再次启动不拉取新上游。源码或补丁更新后使用 `docker compose up -d --build`，普通 `up -d` 不保证重建已有镜像。

## 4. 运行架构与数据所有权

| 服务 | 职责 | 不承担的职责 |
|---|---|---|
| `console` | 静态页面、管理会话、同源/CSRF 校验、管理接口代理、公共模型 API 代理 | 不执行签到算法，不启动第二套排程，不直接读写上游凭据 |
| `core` | 原有模型网关、账号池、凭据刷新、原有 scheduler、OAuth 和任务适配扩展 | 不提供对外管理页面，不绕过用户执行浏览器验证 |

仅 `console` 映射宿主机端口，默认 7863；`core` 只在 Compose 网络提供服务。HTTP 代理保留 SSE 流式行为、取消传播和客户端错误语义。公共 `/v1` 与 `/status` 保持原有 API Key 鉴权，不能因为经过 console 就自动注入内部凭据让匿名用户调用。

管理接口采用固定路由和任务白名单，console 与 core 之间使用独立桥接密钥；这个密钥与管理密钥、公共 API Key 不同，不返回浏览器。即使在内部网络也校验桥接鉴权。两个服务不挂载 Docker socket，不接受任意命令、任意脚本路径或任意代理目的地址。

账号文件、账号池状态和任务记录归 core 的持久化卷管理。原有 Python 脚本作为 core 内部受控子进程运行，不能把“只由 core 管理”误解成忽略子进程读写协调。console 只保存自己的管理配置；服务间密钥通过权限受限的部署凭据卷提供，凭据卷不包含账号令牌。

首次启动由 core 初始化所需目录与独立密钥，console 等待初始化完成后读取自己的管理配置。初始化幂等、原子写入；已有文件损坏时明确失败，不自动轮换密钥。预设环境变量保持受校验的覆盖能力。首次生成的管理密钥仅在 console 启动日志中按已有约定输出；上游令牌和桥接密钥不输出。

两个服务均以非 root 用户运行。console 与 core 分别提供进程存活检查；空账号不构成启动失败，保留 core `/healthz` 表达账号可服务性。公网管理访问通过 HTTPS 代理，显式配置公开 origin，不无条件信任客户端的转发头。

## 5. 扩展与补丁范围

### 5.1 移出上游的功能

现有网页、管理登录、会话、CSRF、API 展示和代理逻辑迁入 `console/`。OAuth 流程、账号安装适配、任务记录和内部桥接端点放入 `extensions/`，不直接保存在纯净上游目录中。

Web OAuth 的 state、cookie jar、上游令牌和账号安装由 core 扩展持有。console 只转发授权链接和脱敏进度。流程绑定管理会话，退出通过桥接取消该会话下的流程；临时内存流程在服务重启后失效，用户可重新发起，已保存账号不丢失。

### 5.2 允许的上游补丁

- 主程序接入扩展：把已有 pool、upstream、scheduler、有效配置和退出 context 交给桥接层，不重写整份 `main`。
- scheduler 的统一执行挂接与结果观察：让定时任务也经过记录和互斥入口，保留上游的时间计算与任务实现。
- 任务结果与脚本输出的必要观察点：提供明确的成功、失败、跳过或未确认信息，不依靠 UI 猜测进程退出代表全部成功。
- 安全热安装与凭据并发协调所需修复：保留 live Auth 身份，阻止旧刷新覆盖新授权；待激活账号在重启、选号、兜底和出站窗口均不可路由。
- 经回归测试证明仍必要的兼容修复。可由初始化或新增文件解决的问题不额外修改上游。

每个补丁记录目的、基线、改动路径、验证入口及何时可因上游已支持而删除。此前较广的直接修改逐项审查，能迁为扩展的迁为扩展，不把现有 diff 原封不动封装成一个大补丁。

### 5.3 必须保留的现有行为

- OAuth token 端点的 `11217` 是等待登录，不是终止失败；未知错误仍正常报错。
- 新账号保存成功后热安装，无需重启；国际版由用户选择地区，未完成激活的凭据可保存但不可参与请求。
- 重新授权只解除明确的登录失效禁用，不清除无关模型限流；刷新、保存和出站使用一致凭据快照。
- 管理会话与公共 API 鉴权分离，令牌不出 core；UID、realm、可信授权链接、响应大小与流程过期仍受校验。
- 浏览器停止、断连或流式解析失败时取消请求并释放占用；现有 CLI、原账号文件和公共 API 协议保持兼容。

## 6. 自动任务页面与执行规则

### 6.1 页面范围

导航新增「自动任务」，复用现有中文页面风格与手机布局。页面从 core 获取有效配置和排程，不在前端另写一份默认时间计算。

| 任务 | 默认时间（北京时间） | 说明 |
|---|---|---|
| 签到 | 09:00、21:00 | 签到与余额查询 |
| 猫猫旅行 | 09:00、21:00 | 领养、派出、领奖巡检 |
| 活跃上报 | 10:00 | 沿用上游活跃任务和关联动作 |
| Token 保活 | 22:00 | 凭据刷新，不标为积分收益任务 |
| 开学季 | 12:00 | 沿用既有活动脚本及活动有效性判断 |
| 夜猫子 | 01:00 | 沿用既有时间窗口与领奖判断 |

每类任务展示启用/禁用、配置时间、下次计划时间、是否正在运行、最近结果，以及「立即执行」。任务范围固定为全部符合条件的账号，沿用账号版本、禁用状态、有效凭据、活动窗口及上游限制。没有符合条件的账号时记录跳过，不显示成功领取奖励。

第一版禁用任务的「立即执行」也禁用，避免越过配置中明确关闭任务的意图。网页不修改开关或时间；修改配置仍走部署配置并重启生效。活动未开放、已经领取或不在时段时显示实际跳过原因，不能绕过这些条件强行执行。

### 6.2 只有一套排程与执行入口

core 中已有 scheduler 是唯一排程来源。定时触发和手动请求调用同一个扩展执行入口，再调用同一个 scheduler 实例的既有任务方法。console 不运行 cron，不通过 Docker exec 另起一套账号池或任务进程。

首版后台任务在 core 中统一串行执行，模型聊天不因此全局停机；必要的凭据锁仍需单独协调。正在执行任务时新的手动触发返回忙碌和当前运行 ID，页面禁用按钮；同一计划时点的多个定时任务沿用上游顺序依次执行。同一个任务的定时触发与正在执行的手动运行撞车时，共用当前运行并记录该计划触发，不再重复执行；不同任务撞车时，定时调度等待当前执行完成后依次执行。不静默丢弃计划触发，也不维护持久任务队列。

手动启动是异步请求，接受后立即返回运行 ID，页面轮询结果；关闭页面不会停止一个已接受的后台任务。启动请求携带幂等请求 ID，网络重试查询或返回同一记录，不再次触发奖励动作。该规则不等于禁止管理员之后明确发起一次新的运行，实际可重复执行性继续由上游控制。

定时执行不做停机期间的补跑。重启后从当前时间计算下次时点，之前未结束的记录标记为中断/结果未确认，不自动重放领奖操作。保留上游限速，不新增高频刷分、绕过活动限制或创建账号功能。

### 6.3 记录与真实性

记录包含运行 ID、任务 ID、最初的手动/定时来源、合并的计划触发（如有）、请求 ID（如有）、开始/结束时间、耗时、总体状态、账号结果及有上限的脱敏日志摘要。状态区分运行中、成功、部分失败、失败、跳过、中断和结果未确认。单账号失败不能被后续账号成功覆盖；运行结束不自动等于任务业务成功。

签到优先使用现有结构化返回值，其他任务通过必要的结果观察点归一；Python 脚本保留输出并识别明确结果，无法可靠判断时记录未确认。不能只解析一行 `ok` 或仅依据退出码零宣称已领取积分。

可记录有时间戳的执行前后积分观测，并明确标为余额变化；同时有聊天消费、积分过期等行为时，差额不等于任务奖励。只有上游明确提供的奖励值才能标为本次奖励，缺失值为空而非零。

记录由 core 写入自己的数据卷，首版使用有界的本地 JSON 记录文件，原子替换，不新增数据库服务。默认保留最近 30 天且最多 1000 条，单条日志摘要最多 64 KiB；截断明确标记，正在运行的记录不被清理。历史记录不保存完整 HTTP 报文、Cookie、授权 state、访问令牌、刷新令牌或管理密钥。

写入开始记录失败时拒绝新的手动执行，自动执行本次跳过并告警，避免悄悄产生不可追踪的领奖。执行后记录更新失败时明确告警并保留未结束记录，重启后按中断处理，不用重试任务来修复记录。损坏记录不静默覆写；不影响已有模型 API，任务管理明确报告存储故障。

## 7. 接口契约与错误处理

console 的新增管理接口为 `GET /admin/tasks`、`POST /admin/tasks/{taskId}/runs`、`GET /admin/task-runs` 和 `GET /admin/task-runs/{runId}`。全部要求管理会话，写操作要求 CSRF；结果查询分页且限制每页数量。

core 对应管理能力位于独立内部路由下，含协议版本、账号授权/安装、任务配置、运行和记录查询；不把内部路由作为公共 API 通配转发。扩展版本、上游 commit 和补丁标识由 core 提供给控制台用于诊断。桥接协议不兼容时管理页给出升级不匹配提示，不尝试猜字段后继续执行任务。

未鉴权返回 401，跨源或 CSRF 失败返回 403，非法任务或参数返回 400/404，禁用或执行冲突返回 409，core 不可达或记录不可写返回明确的 503。敏感上游错误只展示脱敏摘要。重复点击、慢请求、网络断连都不允许绕过任务互斥或产生隐式重复提交。

## 8. 手动更新上游

计划提供一个更新入口，接收上游版本或 commit，并解析为完整 commit 后固定记录。升级过程在临时目录准备候选源码，不自动选择最新版，也不修改当前运行的容器。

顺序为：取得候选源码 → 核对来源与清单 → 加扩展并检查补丁 → 运行上游及适配测试 → 构建候选镜像并做隔离的模拟验收 → 更新仓库中的源码快照和锁文件。相关路径存在用户未提交改动时拒绝覆盖，先报告冲突。

任一步失败，保留现有上游快照、锁文件和运行实例；候选目录可用于排查。成功只更新仓库工作文件，供用户审阅和提交，不自动提交、推送或切换线上容器。部署仍是后续明确操作。

回退使用已记录的前一组合：上游 commit + 扩展/补丁版本 + 镜像版本。回退不删除运行数据；本轮新增记录为扩展独立数据，原账号和状态格式优先兼容。不能把一次版本升级宣称为“所有未来上游更新都不会冲突”。

## 9. 当前目录与运行数据迁移

实施在当前目录进行，不创建 worktree。先记录 Git 状态、已提交历史、未提交 diff 和新增源码清单，并制作可恢复备份；不覆盖用户的 `.agents/`、环境配置或其他非本任务文件。

保留现有 Git 历史，以目录迁移建立新的维护边界，不删除或重新初始化 `.git`。当前上游远端不作为定制代码推送目标；新仓库远端由用户之后提供，本次不创建外部仓库、不推送原上游。

将原上游源码还原为基线快照放入 `upstream/`，此前 Web 和安全修复按扩展/补丁清单迁移，不能遗漏新增未跟踪文件。旧设计文档保留并由本设计明确取代相关架构结论。

迁移前解析当前容器真实使用的卷名和绑定路径，不能因 Compose 项目名或服务名变化生成空卷并假装迁移成功。先备份真实使用的数据，再显式复用原账号和账号池状态卷；任务记录保存在独立子目录。保留既有 API Key 和管理密钥，新增桥接密钥。旧 `console-keys.json` 经一次性、可重复且有冲突检查的迁移写入新凭据布局，不记录密钥正文、不自动覆盖已有不同密钥。

不运行删除卷的命令，不清空账号。应用迁移不要求用户重新授权上游账号，但内存中的网页管理会话与进行中的 OAuth 流程会在重建后失效，页面提示使用原管理密钥重新进入或重新发起授权。

源码隔离、数据迁移和模型路径回归验证通过后，再接入自动任务页面。迁移测试使用独立模拟数据卷；在实际容器切换前检查在途请求和任务，不能把测试与实际账号领奖混为一谈。

## 10. 验收与交付顺序

### 第一阶段：上游隔离与现有功能迁移

1. 纯净源码清单可复现；构建前后 `upstream/` 不变；扩展不能覆盖上游同名文件。
2. 错误版本、补丁冲突、重复补丁、候选测试失败均停止，当前版本和运行容器不受影响。

### 第二阶段：自动任务页面

1. 六类任务配置、时区、下次计划时间来自实际 core；禁用任务不能手动越过配置启动。
2. 定时与手动运行均入记录，复用同一 scheduler 实例；并发点击、同一请求重试、定时撞车不会重复执行。
3. 全部符合条件的账号按上游限制执行；禁用、不支持的版本、活动结束、窗口外、已领取和无账号均准确显示跳过。
